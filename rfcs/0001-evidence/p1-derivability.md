# P1 (agent 3): The derivability surface of an emlang Event Model

Purpose: fix exactly which navigation, enablement and idiom facts a transformer can compute from the Event Model alone, so that admission test 1 (Derivability) can be applied mechanically by later agents. Sources: eventmodeling.org, Dymitruk interviews, Dilger's book (TOC and secondary summaries only; the book text was not fetched), the emlang spec v1.0.0 and schema, the local .NET parsers, the three fixtures, and the three kvissig Experience Models.

Abbreviations: BB = `C:\code\GitHub\xmlang\tests\Emlang.Tests\fixtures\blindbudet.em.yaml`, MEM = `...\mer-eller-mindre.em.yaml`, TTT = `...\tank-till-tusen.em.yaml`, XM-BB/MEM/TTT = `C:\code\GitHub\kvissig.se\specs\{blindbudet,mer-eller-mindre,tank-till-tusen}.xm.yaml`, SPEC = https://raw.githubusercontent.com/emlang-project/spec/main/SPEC.md, XSPEC = `C:\code\GitHub\xmlang\xmlang-spec.md`, EMP = `C:\code\GitHub\xmlang\src\emlang\Emlang\EmParser.cs`.

## Lead findings

1. **emlang the language carries five element kinds and nothing else.** The spec's root is `slices` only (SPEC L13); an element is exactly one type key plus free-form `props` (SPEC L37-40, L86; `schema.json` `additionalProperties: false` on `element`). There is no screen, state, phase, role, enum, navigation, error-audience or compensation construct. Everything richer in the fixtures (phase enum, `State /` and `Todo /` lanes, actor-plus-origin triggers, emoji slice types) is **convention layered on free text**, parsed by local tools, not by the spec.
2. **Enablement at phase granularity is derivable; enablement per viewer is not.** The `phase` enum on the `State /` view plus the `given` clauses of successful GWT cases yield, for every command, the set of phases in which it succeeds. The per-viewer predicates (has this player already bid?) exist in the model only as exception *names* (`x: AlreadyBid`); the predicate itself is decider code. This confirms H-B's shape: the coarse dialog model lives in emlang; the fine one lives nowhere writable.
3. **Post-command destination is derivable only as "the slice's terminal view", under an order convention the spec does not state.** SPEC L97 calls a slice "a named sequence of elements"; only the linter gives order any meaning (command should be followed by event, `Linter.cs` L53-57). Every `✍️` slice in the fixtures ends in a `v:` (BB L136, L204, L270, L361, L547, L786, L825), so the convention holds on the testbeds, but a transformer relying on it is applying a heuristic.
4. **Source surface (where a command is issued) is not a resolvable reference.** The trigger `t: 🧑‍🎓 Player /Lot` (BB L343) names an originating screen by local convention (BB L7-8) as free text; `EmParser` keeps only the lane as a role (EMP L104-107, L116-121) and discards the name. "Lot" does not resolve to the view `Lot card` (BB L305). This is the single cheapest gap that could be closed *in emlang* and would make navigation topology largely derivable.
5. **Automation-driven change and read-only posture are fully derivable**; destructive/irreversible, compensating commands, wizard grouping, optimistic-vs-confirmed and inline-vs-modal are not, and on the three testbeds most of them also have **no instance** (no undo, no delete, no command with more than four props), which pre-empts admission test 2.
6. **Event Modeling treats the wireframe lane as part of the blueprint but as an information-completeness instrument, not as a UX or navigation artifact.** Dymitruk: "UX/UI is a primary concern. The screens are a core part of the system" and "each field must be represented so that the blueprint ... has the source of and destination of the information" (InfoQ; eventmodeling.org). The method forbids stacking screens ("There are no screens that appear above one another") and models flow only as left-to-right time in swimlanes. emlang drops the lane entirely (the emlang site documents no screen construct), and xmlang's `xm-screen-lane-view` lint (XSPEC L294; `XmLinter.cs` L83-85) treats a screen-named view as a smell. Navigation therefore *belongs* to no current stratum: the method carries it as picture order, emlang as slice order, xmlang as `journeys` (test material, XSPEC L188).

## 3. Event Modeling's stance on screens, and emlang's

**The method.** The wireframe row is part of the blueprint, not decoration: "Add screens, mock-ups or wire-frames above the row of events to show what the users of the systems see" and "UX/UI is a primary concern. The screens are a core part of the system as it also addresses the needs of people who are more visual than analytical" (Dymitruk, https://www.infoq.com/news/2020/09/adameventmodeling/). But its job is *information completeness*: "each field must be represented so that the blueprint for the system has the source of and destination of the information represented from the user's perspective" (https://eventmodeling.org/posts/what-is-event-modeling/), and "it shows if you are 'information complete'. This means you can connect all the example data in the model identifying where it came from and where it's going to" (InfoQ). Two structural rules follow: screens sit in swimlanes per user ("divided into separate swimlanes to show what each user sees", what-is-event-modeling), and screens are never stacked ("There are no screens that appear above one another as we need to capture each change in the system state as a separate vertical slice", same page). The cheat sheet reduces the trigger's UI to "simple wireframe or the route of an http endpoint" (https://eventmodeling.org/posts/event-modeling-cheatsheet/). Dilger's book is reported to say the wireframes are "there to clarify data and behavior, not to finalize UX, and should be kept intentionally rough" and that drawing one should take "a maximum of two minutes" (secondary summary from search results; book text not fetched — [citation needed] for the exact wording; chapter 12 is "Modeling Use Cases with Wireframes", https://www.eventsourcingbook.com/).

Consequences: the method carries **which fields** a screen shows and **which user** sees it; it carries **flow** only as left-to-right time along one example narrative. It has no vocabulary for "after this command the user goes to that screen" except that the next slice's wireframe is to the right, nor for enablement beyond the GWT of the command. The four patterns (state change, state view, automation, translation; cheat sheet) are per-slice; cross-slice navigation is emergent from ordering.

**emlang.** Drops the wireframe row. The trigger keeps the screen as a *name* (`t: Customer/RegistrationForm`, SPEC L76, L117; `t: Customer/ProductPage # User clicks "Buy Now"`, L272), which is the only place a screen survives, and the spec attaches no semantics to the text after the slash. The fixtures once had a `Screen /` view lane; xmlang v0.2 added `xm-screen-lane-view` (info, suppressible: "the Event Model names surfaces rather than data", XSPEC L294; implemented at `XmLinter.cs` L83-85 on `view.Lane == "Screen"`) and `xm-surface-shadows-view` (L291; `XmLinter.cs` L54-56). All three testbeds then renamed screen views to data nouns (XM-BB finding 1, L7-9; today `grep 'Screen /'` returns 0 in all three fixtures). So the local doctrine is: **views are data, surfaces are xmlang's**, and the trigger's origin text is the vestige of the wireframe row.

**Implication for navigation.** Neither stratum owns it. The method's answer is "look right along the timeline"; emlang's answer is slice order plus the trigger's origin text; xmlang's `journeys` is explicitly "material for generated cross-slice walkthrough tests" (XSPEC L188), not a sitemap, and `compose` "restricts nothing, it only aggregates" (L180). The Defaults table says "one surface per slice" (L257), which *is* an implicit navigation model: one node per slice, edges by slice order. Row 1 of the table is therefore the default topology; the question for the team is only whether the residue (rows 2, 3, 12, 13-grouping) is judgment or missing emlang data. The evidence here says row 3 is missing emlang data and rows 2, 12, 13 are judgment with, on these testbeds, no non-default instance.
