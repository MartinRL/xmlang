# P1 / agent 2 — Interaction judgments named by IA and IxD literature

Scope: catalogue the decisions that information architecture and interaction design treat as first-class, then sort each into DATA (membership / order / tier / closed enum), GEOMETRY, BEHAVIOUR (Event Model), or IDIOM (concrete rendering). Sources were fetched 2026-09-07; where a primary text was unreachable (Medium, O'Reilly, designinginterfaces.com all refused fetches) I quote via a secondary page and say so. Quotes from Rosenfeld/Morville/Arango 4th ed. and the About Face ch. 12 slide deck come from text extracted from PDFs found in the searches (`rosenfeld.txt`, `cooper.txt` in this scratchpad).

## Findings first

1. **The literature names about 45 judgments; only ~12 survive as plausibly DATA-not-geometry, and most of those are one-key residues of navigation (sense A) and reversibility (sense C).** Sense B (dialog/state) has no independent vocabulary in this literature at all: Garrett's "conceptual model", Norman's conceptual model, and Nieters' "objects and actions" are all descriptions of what the Event Model already is.
2. **"Interaction model" in IA/IxD practice is Saffer's and Nieters' term for navigation-plus-object-model, not for a state machine.** Saffer: interaction models are "the means to access and move between functions" ([Saffer, via search summary of Medium article](https://odannyboy.medium.com/interaction-models-e9a88987b893)). It is sense A with a whole-product enum flavour (list, hub, feed…), never a per-command predicate.
3. **Event Modeling already fixes the unit of the interaction model: one screen per state change.** "There are no screens that appear above one another as we need to capture each change in the system state as a separate vertical slice" ([Dymitruk, LinkedIn](https://www.linkedin.com/pulse/event-modeling-designing-modern-information-systems-adam-dymitruk)). That is exactly xmlang's default "one surface per slice"; the storyboard order of slices on the timeline is an implicit sequential navigation the current spec does not exploit.
4. **The strongest recurring candidates are: entry surface per persona; the destination after a command (stay vs advance); wizard step grouping; posture; confirm-vs-undo; and rejection copy.** Each has a real counter-argument, listed in §4; two of them (undo pairing, irreversibility) look like emlang findings rather than xmlang.
5. **The most common failure mode in the catalogue is disguised geometry**: Tidwell's Modal Panel, Two-Panel Selector, List Inlay, One-Window Drilldown, and Cooper's transient posture all name a *container* and only incidentally a judgment.

## 2. Garrett's structure plane against the xmlang/emlang split

Garrett's own framing: on the structure plane "the Web-as-software-system discipline of interaction design and the Web as hypertext-system-discipline of information architecture come into play. These elements inform the skeleton plane, where information design is a global concern that specializes into interface design… and navigation design" ([ACM Interactions 2003](https://interactions.acm.org/archive/view/september-october-2003/the-elements-of-user-experience1)). Interaction design "describ[es] all the possible behaviors that the user can have while using your site, defining how the system will handle it, and respond to it" ([Pesce summary](https://medium.com/@robertopesce/ux-structure-garrett-day-8-102af15727b7); primary wording `[citation needed]`, book ch. 5).

| Plane | Garrett's contents | Where it lives today | Gap |
|---|---|---|---|
| Strategy | user needs, product objectives | out of scope (personas `props` carry goals) | none intended |
| Scope | functional specs, content requirements | **emlang**: commands, events, views, GWT scenarios | none |
| Structure — interaction design | conceptual model; "how the system will respond"; error handling (prevention / correction / recovery) | **emlang**: the decider, command→event→view, rejection scenarios | *Response destination* (what the user sees next) is implied per slice but not chosen; *correction* display is concrete |
| Structure — information architecture | architectural approach (hierarchical/matrix/organic/sequential); nodes; top-down vs bottom-up | **xmlang partially**: `surfaces` = nodes, `for`×`during` = which nodes exist when; `journeys` = a sequential structure used only for tests | *Topology* (how nodes connect; entry node) is unrecorded; xmlang has nodes without edges |
| Skeleton — information design | grouping, prioritising information | **xmlang**: salience tiers, compose order | none |
| Skeleton — interface design | selecting and arranging elements | **xmlang** selects (`compose`, `prominence`); arranging is the concrete stratum | none intended (geometry prohibition) |
| Skeleton — navigation design | the screen elements for moving through the IA | concrete stratum | depends on the topology gap above: a transformer can only render edges it can infer |
| Surface | sensory design | `tokens` + concrete stratum | none intended |

So the "structure plane gap" is narrower than Garrett's plane: interaction design is essentially the Event Model, and of information architecture only the *edges* (topology, entry, after-command destination) are missing. Note Garrett's deliverables for this plane are flow charts and site maps ([UX Design Institute](https://www.uxdesigninstitute.com/blog/5-elements-of-ux-design/)); the Defaults section of the spec already claims xmlang replaces "a sitemap, a journey map" — but only journeys exist, and a sitemap is an edge list.

## 3. Terminology: how "interaction model" is used

- **Saffer** (2019, Medium; quotes as returned by search summary because Medium blocks fetches): interaction models are "the means to access and move between functions" and "the overarching framework that ties the functionality together into a unified whole"; "Interaction models are the designer's attempt to help the user generate a mental model of the device" ([source](https://odannyboy.medium.com/interaction-models-e9a88987b893)). Sense A, whole-product, enumerable (list, hub, feed…) `[example list: citation needed]`.
- **Nieters** (UXmatters 2012): "An interaction model is a design model that binds an application together in a way that supports the conceptual models of its target users"; it "defines how all of the objects and actions that are part of an application interrelate, in ways that mirror and support real-life user interactions"; "the glue that holds an application together" ([source](https://www.uxmatters.com/mt/archives/2012/01/defining-an-interaction-model-the-cornerstone-of-application-design.php)). Objects + actions + navigation pathways: senses A and B together, still no predicate language.
- **Rosenfeld/Morville/Arango** use the phrase once and informally: devices with different constraints mean the user "doesn't experience them as a consistent, coherent interaction model" (`rosenfeld.txt` l. 889–891). Their own first-class terms are organization *structure*, *scheme*, and *navigation system*.
- **Built In** (secondary): interaction models "try to inform the way the product behaves with users and visualize the interactions based on the mental model of the users" ([source](https://builtin.com/design-ux/interaction-model)).
- **Distinction from mental/conceptual model**: "mental models are discovered (through research), conceptual models are designed (through intention)" ([Glow Team](https://glow.team/blog/mental-models-vs-conceptual-models)); Norman's conceptual model is the designer's "coherent, consistent system image" ([search summary of DOET](https://medium.com/10x-curiosity/don-norman-and-the-design-of-everyday-things-d187e6a81fd8)). In practice the *interaction model* is the navigational and object-action skeleton the designer builds so that the user's mental model converges on the designer's conceptual model. In xmlang terms: conceptual model = Event Model; interaction model = the edges between surfaces plus how actions are reached — sense A with a thin C layer, and never sense B as MBUI meant it (dialog/state machines). Dubberly et al. use "interaction" in yet another sense (system coupling types) that does not bear on UI vocabulary ([source](https://www.dubberly.com/articles/what-is-interaction.html)).

## 4. Top 10 DATA-not-geometry candidates, ranked

1. **Entry surface per persona** (Tidwell Clear Entry Points / Instant Gratification; Rosenfeld global nav; Cooper primary persona). `personas.X.entry: Surface`. Membership; not derivable when several surfaces are active in the initial `for`×`during` cell. *Counter*: derivable as the first slice on the EM timeline for that swimlane ("no screens above one another… each change a separate vertical slice" — Dymitruk), so it fails Derivability unless emlang loses slice order; also dead weight for single-surface phases.
2. **Destination after a command: stay vs advance** (Norman gulf of evaluation; Garrett "how the system will respond"; Nielsen H1). `c: X` → `then: stay | <Surface>`. *Counter*: the slice's own view is the natural destination (command→event→view), and `then:` naming a surface is the first edge of a sitemap graph, which demands `back:` next (Slope). Closed-enum form `then: stay | advance` avoids the graph but may restate defaults (Dead weight).
3. **Wizard step grouping** (Tidwell Wizard; Rosenfeld walkthroughs; Garrett sequential). `steps:` as an ordered partition of a command's fields. *Counter*: Event Modeling says a wizard with one committing event has no intermediate state, so steps are pure concrete UI; and a "step" is a container, i.e. disguised geometry — the geometry experiment's slope in another coat.
4. **Posture** (Cooper). `surfaces.X.posture: sovereign | transient | auxiliary`. Closed enum, genuinely non-derivable (a waiting view can be either). *Counter*: transient "comes and goes… tightly restricted set of controls" is a size/container description ([Wikipedia](https://en.wikipedia.org/wiki/Application_posture)); daemonic has no surface at all; for a game app nearly every surface is sovereign (Dead weight).
5. **Confirm vs do-don't-ask** (Cooper modal excise; Nielsen H5; Tidwell). `c: X` → `confirm: true`. *Counter*: Cooper's own rule makes it derivable — confirm only when no undo exists — so the datum is *irreversibility*, a domain fact that belongs on the emlang command, not in xmlang.
6. **Undo pairing / compensating command** (Cooper undo chapter; Nielsen H3; Tidwell Safe Exploration). `c: PlaceBid` → `undo: WithdrawBid`. *Counter*: "WithdrawBid compensates PlaceBid" is behaviour; the one-way rule says record it in the Event Model and let xmlang read it. Strong emlang finding.
7. **Rejection copy** (Nielsen H9; Garrett error handling; Cooper audit-don't-edit). `labels.<locale>.<Command>.$rejected.<Scenario>`. Copy is never derivable. *Counter*: only a new *reserved key*, and only if emlang exposes rejection-scenario names; zero new root vocabulary, so it is a labels extension rather than an Interaction Model item.
8. **Contextual / related surfaces** (Rosenfeld contextual nav; Garrett matrix/organic). `surfaces.X.related: [Y]`. *Counter*: Dymitruk's information completeness gives field lineage, so most "see also" edges are derivable from shared identity fields; the rest is the sitemap-graph slope again.
9. **Whole-product navigation structure** (Garrett architectural approach; Rosenfeld structures; Tidwell hub-and-spoke; Saffer interaction model). Root `navigation: hub | sequence | flat`. *Counter*: one value per product is the definition of dead weight, and it is largely derivable (linear phases → sequence; many surfaces per cell → hub); a human transformer will ignore it (Transformer neutrality weak).
10. **Primary persona** (Cooper). `personas.X.primary: true`. *Counter*: with two or three personas, map order already expresses it; `for:` does the actual work.

Demoted from consideration: collection sort order (Rosenfeld exact schemes) — a `format:`-class hint; Modal Panel, One-Window Drilldown, Two-Panel Selector, List Inlay — containers; modeless feedback, breadcrumbs, escape hatch, deep links — renderings or defaults.
