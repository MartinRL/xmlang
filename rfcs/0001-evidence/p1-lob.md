# P1 (agent 11): The line-of-business testbed — accounts payable

Files: `lob-ap.em.yaml` (Event Model, 33 slices, `em parse` OK, `em lint` 0 errors / 13 `slice-missing-event` warnings on view-only slices, identical to what the shipped fixtures raise) and `lob-ap.xm.yaml` (Experience Model, `xm lint` OK: every reference resolves, all nine `phase` values covered; a deliberately broken control file produced `xm-dangling-ref` / `xm-unknown-phase` errors, so the clean pass is load-bearing). Both in this scratchpad directory. Abbreviations: EM = `lob-ap.em.yaml`, XM = `lob-ap.xm.yaml`, DERIV = `im/p1-derivability.md` (row numbers refer to its §2 table), RES = `im/p1-residue.md` (R-ids), XSPEC = `C:\code\GitHub\xmlang\xmlang-spec.md`, EMP = `C:\code\GitHub\xmlang\src\emlang\Emlang\EmParser.cs`.

## Lead findings

1. **The LOB model produces genuine non-default annotations where the games produced none.** Entry surface per persona differs from the derivable default for 2 of 4 personas (W-14); post-command destination differs from "the slice's terminal view" in 3 of 24 state-change slices because the terminal view is `Invoice details` *of a different invoice* (W-10/11); destructive confirmation is wanted on 4 commands of which only 2 are derivably irreversible (W-5). Admission test 2, re-scoped by the amendment, is passable on this model for those three.
2. **`during` does not mean what the spec says once there is more than one object.** XSPEC L109 defines `during` as "when in the system's lifecycle the surface is active"; in AP, `phase` is the phase of *one invoice* among thousands, and there are two deciders. `EmParser.PhaseValues` unions every `State /` view's `phase` enum (EMP L145-151), so the supplier lifecycle had to be renamed `status` to avoid namespace collision. This is the single cheapest spec fix the testbed exposes (W-1) and it is a *B* (dialog) item that is neither `when:` in disguise nor derivable.
3. **Per-viewer enablement moved into the read model, exactly as H-B predicts.** `Approval queue` projects `pending` vs `blocked` *per approver* (EM `👀 Approval Queue`), so `CannotApproveOwnInvoice` and `ExceedsApprovalLimit` never need an xmlang predicate: the view already tells the viewer what she can act on. LOB read models routinely absorb per-viewer enablement; games rarely bother. This weakens the case for any `when:` and strengthens "belongs in emlang".
4. **List parameters are a hole in emlang, not xmlang.** `Invoice list.phaseFilter/supplierFilter/query` are *inputs* to a projection, but emlang's `props` has no way to mark a view prop as a parameter rather than projected data (W-20). Every enterprise list report has them; every xmlang tier annotation on them is category error.
5. **Row-scoped and selection-scoped commands are the LOB shape xmlang cannot compose.** `ApproveInvoice` acts on one `pending` row; `ApproveInvoices` acts on a selection of them (W-3/4). The id-name match (`invoiceId` on both) is a derivability heuristic (DERIV row 20) that a transformer *can* use; whether it should be vocabulary depends on whether ambiguity arises in practice — on this model it does not (every row type carries exactly one id that matches a command prop).
6. **Recurrence across ≥3 enterprise design systems** is strongest for: destructive confirmation, unsaved-changes/draft handling, list-detail-edit navigation pattern, wizard-vs-form for long create flows, bulk selection actions, reason-on-reject, display-vs-edit posture, empty/loading/error states, message channel (toast/inline/dialog), and navigation after save. Of these, the design systems treat most as **per-page/per-action judgments the app designer makes**, not system-wide defaults — the same signal xmlang's admission tests look for. See §3.

## 1. The model in brief

**Roles (swimlanes):** `🧾 Clerk` (register, correct, schedule), `✅ Approver` (approve/reject/void within a limit), `🔍 Controller` (read-only auditor who owns the dispute hold), `🛠️ Admin` (supplier master data), `⚙️ System` (payment run, approval reminders).

**Two deciders:** `State / Supplier` (`status: active|inactive`, `version`, `openInvoiceCount`) and `State / Invoice` (`phase: InvoicePhase (draft|submitted|onHold|approved|rejected|scheduled|paid|voided|discarded)`, `heldFromPhase`, `createdBy`, `totalAmount`, `version`).

**Slices (33):** 5 supplier (create, edit, deactivate, reactivate + directory/details views), 6 invoice registration (draft, edit draft, discard, submit, withdraw, reopen), 4 approval (approve, reject, bulk approve, queue view), 2 dispute (hold, release), 5 payment (schedule, `📋 Due payments`, `⚙️` payment run, log view, reverse), 1 void with compensating `Ledger / LiabilityReversed`, 2 long-running reminder (`📋 Stale approvals`, `⚙️` remind), 5 screen views (list, details, outstanding, cash position, audit trail), 2 decision models. Every editing command carries `expectedVersion` and raises `x: ConcurrentEdit`; every reason-bearing command raises `x: ReasonRequired`; the per-viewer guards `x: CannotApproveOwnInvoice` and `x: ExceedsApprovalLimit` have GWT cases.

**Experience Model:** 4 personas, 24 surfaces (the `Invoice details` view is composed eleven times across the `during × for` lattice — the LOB analogue of `LobbyVärd/LobbySpelare` at scale), 7 journeys, `en` labels with `$empty` copy on every list, DTCG tokens including status colours named by phase value *by convention only*.

**Reading the list against the hypotheses.** H-A (navigation mostly derivable, small residue) holds: entry per persona (W-14), advance-to-next vs stay (W-10/11) and hub links (W-21) are the residue; master-detail (W-15) is id-derivable here. H-B (dialog model lives in emlang) holds *more strongly* on LOB than on the games: W-6, W-8, W-23 all resolve into the EM; the one B item xmlang genuinely lacks is a phase *namespace* (W-1), which is a reference-resolution fix, not a predicate language. H-C (a few idioms are data) holds: destructive confirmation (W-5) and command-prop grouping (W-2) are judgment; reason-first (W-7), waiting (W-19), and edit-form-of-view (W-9, partly) are derivable.

**Slope and geometry checks on the ★ items.** `entry` (W-14): one boolean per surface or one surface name per persona; demands nothing else. Post-command destination (W-10/11): a closed enum `stay | return | next` on a command item; `next` presupposes an ordered list the command was launched from — which is W-3/4's row binding, so *this key does pull a second one* (slope warning). Confirmation (W-5): a boolean pulls confirmation copy, but `labels` already has reserved keys (`$empty`), so `$confirm` is a labels extension, not a new axis. None of the three names a container, region or placement.

**What recurs across ≥3 systems and is a per-action judgment there:** destructive confirmation by impact tier (6), wizard/grouping thresholds (6), navigation after save (4), status criticality per value (4), which fields filter (3). **What recurs but is a system-wide default in the DS itself** (so fails the "judgment" test regardless of derivability): message channel (7), disabled-vs-hidden rule (5), loading thresholds (5), display/edit posture (3 of 5). **What no DS names** — mandatory reason, audit disclosure, concurrency UX — are application-logic facts that the Event Model already carries.

The convergence with §2 is tight: the four ★ items of the wish list (`entry`, `then`, `impact`, and the phase namespace) map onto the four DS-recurrent per-action judgments plus one spec-fix, and Fiori already ships two of them as configuration data (`stayOnCurrentPageAfterSave`, `Criticality`). `entry` per persona has no DS analogue because design systems address one app at a time; it is a role-based-product judgment, which is why the games (one entry per role) never showed it.

## 4. Notes for the team

- **Use `lob-ap.em.yaml` as the test-2 testbed.** It is valid emlang (`em parse` OK) and the xm resolves against it (`xm lint` OK), so candidate keys can be dropped into `lob-ap.xm.yaml` and linted the moment the reference linter learns them.
- **One modelling finding belongs to emlang, not xmlang:** view parameters (W-20). A second is a spec-wording fix in xmlang: `during` should resolve against a *named* decider's `phase`, because LOB models have several (W-1, EMP L145-151).
- **Negative control preserved.** Every ★ item is dead weight on the games (one entry per role, every command advances to its slice's terminal view, no destructive command, one decider), which is precisely the amendment's "dead weight on games alone does not fail" case.
- **Uncertainty.** Fiori citations are snippet-level because of the 403; the two SAP-docs GitHub files (draft handling, status colours) are full reads and carry the load-bearing claims (`stayOnCurrentPageAfterSave`, Create Next, `Criticality`). Redwood is under-evidenced.
