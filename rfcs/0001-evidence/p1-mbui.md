# P1 — How MBUI expressed dialog and navigation, and why it failed

Phase 1, agent 1. Literature report for the Interaction Model question (senses A/B/C in BRIEF.md). Primary texts were fetched and read where possible (Myers 2000 draft PDF, Cameleon D2.1, UsiXML 2004, CTT 2003 handbook chapter, MARIA Interact'09, Schlungbaum 1996, W3C MBUI Notes and XG report). Where only an abstract or a secondary summary was reachable, this is said.

## Findings first

1. Every MBUI dialect had **two** dialog-ish constructs, never one: a *task-level* temporal algebra (CTT operators, LOTOS-derived) and a *presentation-level* state machine (transition tasks, connections, ECA rules, StateWebCharts). The first duplicated the application's own behaviour model; the second grew into a programming language. Neither was ever the "small residue" xmlang's brief hopes for.
2. Navigation was almost never authored. Cameleon/TERESA/ARTStudio *derived* it: Enabled Task Sets → Presentation Task Sets → "transition tasks" between them ([Cameleon D2.1 §1.2.3](http://giove.isti.cnr.it/projects/cameleon/doc/CAMELEON%20D2.1.pdf)). The authored residue was a hand override of the derived scheme ("the designer can override the default navigation scheme", D2.1 p.23). That is direct evidence for hypothesis H-A (navigation mostly derivable, small residue).
3. The "abstract container" was a screen. ARTStudio's *workspace* was "isomorphic to the task model" and then "mapped into a window or into a canvas depending on the navigation interactor used" (D2.1 pp.20–22). Cameleon's AUI containers were window geometry with the pixels removed, which is why the geometry prohibition is the correct dividing line.
4. Myers' verdict on the whole family stands: unpredictability, high threshold, low ceiling, and "the generated user interfaces were generally not as good as those that could be created with conventional programming techniques" ([Myers, Hudson & Pausch 2000 §2.3.4](http://www.cs.cmu.edu/~amulet/papers/futureofhci.pdf)). What "fell off the cliff" was not forms; it was everything whose interaction was not a form.
5. What survived in industry writes down exactly three dialog/navigation facts as data: **(a)** a state × event → next-state table (statecharts: SCXML, XState, Sketch.systems), **(b)** a trigger → destination graph over screens (Figma flows, wireflows), **(c)** a per-command *post-command destination convention* (Rails `redirect_to @record` after create; htmx `hx-target`/`HX-Redirect`). Everything else went back to code.

## 2. Recurring failure mechanisms (attack vectors for the red team)

**F1. The dialog model becomes a programming language.** Starting with "when can this be invoked", every dialect ended with events, conditions, actions, scripts and Boolean-composed transitions: UIDE pre/post-conditions; UsiXML graph-transformation rules and ECA state machines; MARIA's dialog model with CTT operators *plus* abstract scripts and conditional connections; W3C AUI's AbstractListener ECA rules. The moment a `when:`/condition appears, the model has to express the predicate language, and the predicate language has to grow to whatever the product needs. *Exhibited by:* UIDE, UsiXML, MARIA, W3C AUI. *Source:* [Limbourg 2004](https://www.pst.ifi.lmu.de/~baumeist/icwe/ws/ws4/DIWE2004-Limbourg.pdf) ("behaviour specification… is also done with graph transformations rules"); [MARIA Interact'09 p.7](https://opendl.ifip-tc6.org/db/conf/interact/interact2009-1/PaternoSS09.pdf); [W3C AUI](https://www.w3.org/TR/abstract-ui/).

**F2. The task model duplicates the domain/behaviour model.** Foley, quoted by Schlungbaum: "some information has to be specified twice, once by the software engineer and once by the user interface designer… avoid potential inconsistencies between the dual specification." Schlungbaum adds that task pre-conditions/effects require the designer to understand the domain model, so "the development of the task model and of the domain model is interrelated". CTT's operator algebra is a process description of what the system permits — which is precisely what an Event Model with deciders, phases and GWT scenarios already is. *Exhibited by:* all task-model-driven dialects (CTT/TERESA/MARIA, UsiXML, MOBI-D). *Source:* [Schlungbaum 1996](https://repository.gatech.edu/server/api/core/bitstreams/40d91981-35ff-4759-a792-93afd8ba23bb/content) pp.9–10.

**F3. Abstract containers are geometry in disguise.** ARTStudio workspaces map to window/canvas by navigation interactor; TRIDENT "presentation units" were "abstractions of windows"; UsiXML's abstract containers carry spatio-temporal and adjacency relationships. The AUI level promised modality independence and delivered windows with the pixels removed. *Exhibited by:* Cameleon/ARTStudio, TRIDENT, UsiXML, W3C AUI Composition. *Source:* [Cameleon D2.1 pp.20–22](http://giove.isti.cnr.it/projects/cameleon/doc/CAMELEON%20D2.1.pdf); [Schlungbaum 1996 p.13](https://repository.gatech.edu/server/api/core/bitstreams/40d91981-35ff-4759-a792-93afd8ba23bb/content).

**F4. Derived navigation is too modal, so heuristics — then humans — take over.** Cameleon: direct ETS→presentation mapping "can generate excessively modal user interfaces or interfaces with a very limited number of elements", hence grouping heuristics, hence "the designer can override the default navigation scheme". MOBI-D made the mapping interactive from the start. The judgment lived in tool heuristics and hand overrides, never in the model. *Exhibited by:* TERESA, ARTStudio, MOBI-D. *Source:* [D2.1 §1.2.3, p.23](http://giove.isti.cnr.it/projects/cameleon/doc/CAMELEON%20D2.1.pdf); [MOBI-D](https://www.semanticscholar.org/paper/9a9b86488ccb64276fdbe47d5322ee27144ac835).

**F5. Combinatorial explosion of context adaptation.** UsiXML's context = user × platform × environment, driving a *transformation model* rather than a data model ("hundreds of rules"); Cameleon's plasticity example needs different navigation depth per screen size. Every axis of adaptation multiplied the models to author. *Exhibited by:* UsiXML, Cameleon, fourth-generation MBUID. *Source:* [Limbourg 2004 §7](https://www.pst.ifi.lmu.de/~baumeist/icwe/ws/ws4/DIWE2004-Limbourg.pdf); [Meixner 2011 via Akiki 2014](https://oro.open.ac.uk/39809/1/Akiki_Bandara_Yu_ACMCSUR2014.pdf).

**F6. Unpredictability + high threshold + low ceiling (Myers).** "Programmers must also learn a new language for specifying the models, which raises the threshold of use. In addition, model based systems have a low ceiling… A related problem is that the generated user interfaces were generally not as good." Anything with a heuristic between spec and pixels is unpredictable. *Exhibited by:* every dialect with automatic generation. *Source:* [Myers 2000 §2.3.4](http://www.cs.cmu.edu/~amulet/papers/futureofhci.pdf).

**F7. Moving target.** UIMSs "fell victim to the moving target problem" when the desktop standardised; MBUID re-ran the same bet on multi-device, then on context-awareness, then (W3C 2006) lost to HTML5, whose community "viewed it as competitive rather than complementary". *Exhibited by:* UIMS, MBUID generations 3–4, W3C WG. *Source:* [Myers 2000 §2.3.1](http://www.cs.cmu.edu/~amulet/papers/futureofhci.pdf); [MBUI XG Final Report](https://www.w3.org/2007/uwa/editors-drafts/mbui/latest/Model-Based-UI-XG-FinalReport.html).

**F8. Standard without implementers / tool without users.** "No [tools], so far, implements the MBUID standard"; "Most UIDLs are limited in scope and/or usage, have been stopped or are the property of some companies". Data formats need a transformer that people already run. *Exhibited by:* UsiXML, UIML, W3C AUI/Task Notes. *Source:* [W3C MBUI Intro](https://www.w3.org/TR/mbui-intro/); [XG Final Report](https://www.w3.org/2007/uwa/editors-drafts/mbui/latest/Model-Based-UI-XG-FinalReport.html).

**F9. Interaction-type taxonomies restate the data type.** CTT interaction task types (selection/control/editing), MARIA interactors (single_choice, edit, activator) and W3C AIUs (DataSelectionSupport, TriggerSupport) are all derivable from the field's type and whether it is a command. They were dead weight in the sense of the geometry experiment. *Exhibited by:* CTT, TERESA/MARIA, UsiXML facets, W3C AUI. *Source:* [CTT 2003](http://giove.isti.cnr.it/AssetsSitoLab/publications/2003-A1-07.pdf); [W3C AUI](https://www.w3.org/TR/abstract-ui/).

## 3. What survived, and what it writes down as data

| Survivor | Dialog/navigation facts written as **data** | Left to **code** | Why it survived |
|---|---|---|---|
| **Statecharts** — Harel 1987; Horrocks 1999; SCXML (W3C Rec. 2015); XState; Sketch.systems | State hierarchy, events, transitions, guards, entry/exit actions as *names*. Statecharts "inject themselves between the event being generated and the action being performed"; presentation is a consequence ("the field now gets the class based on the current state"). Sketch.systems: states + events + transitions in "Markdown-like notation", exportable to XState; "does not yet support actions or guards". | Rendering, layout, what an action *does*. | Single closed vocabulary; no generation of pixels; the same artefact is spec, diagram and runtime. SCXML shipped as a Recommendation because the voice-dialog industry already ran it (CCXML lineage). | [statecharts.dev](https://statecharts.dev/use-case-statecharts-in-user-interfaces.html); [SCXML](https://www.w3.org/TR/scxml/); [XState](https://stately.ai/docs/xstate); [Sketch.systems](https://sketch.systems/); [freeCodeCamp on Sketch.systems](https://www.freecodecamp.org/news/how-to-visually-design-state-in-javascript-3a6a1aadab2b) |
| **Figma prototype flows** | Flow = "a collection of connected frames", with a **starting point** per flow; interactions = trigger (click, hover, key, after delay…) × action: *Navigate to, Back, Scroll to, Open link, Open overlay, Swap overlay, Close overlay, Change to, Set variable, Conditional*. | Everything — it is a prototype, not a spec; the frames are pixels. | Zero threshold; the navigation graph rides on artefacts designers already make. Note the slope: Figma has already grown `Set variable` and `Conditional` (an ECA rule), i.e. F1 in miniature. | [Figma prototype actions](https://help.figma.com/hc/en-us/articles/360040035874-Prototype-actions); [Figma flows](https://help.figma.com/hc/en-us/articles/360039823894-Create-and-manage-prototype-flows) |
| **Wireflows (NN/g)** | Screens as nodes; "an arrow is used to indicate the specific UI component where the user takes action… and points to another wireframe image of what happens as a result". Annotations for back-end effects. | Anything not on the happy path; scaling ("work less well for… a large number of relatively static pages"). | Human-readable; no tool required; sits at exactly the sense-A level. | [NN/g Wireflows](https://www.nngroup.com/articles/wireflows/) |
| **Storybook interaction tests** | Per-component *state* (story args) and a *scenario* (play function: userEvent → expect). Stories are a closed enumeration of the component's interesting states. | Cross-screen navigation; the component's implementation. | Tests, not models: they pin behaviour without generating it — the same posture as xmlang's generated verification. | [Storybook interaction tests](https://storybook.js.org/docs/writing-tests/interaction-testing) |
| **Rails resourceful conventions** | `resources :products` → seven routes; **post-command destination is a convention**: `redirect_to @product` on success, `render :new, status: :unprocessable_entity` on failure. | The convention itself is code in the controller; overriding it is one line. | Convention over configuration: the navigation model is a *default*, not data — exactly xmlang's Defaults table posture. | [Rails Getting Started](https://guides.rubyonrails.org/getting_started.html) |
| **htmx / hypermedia** | Per-element `hx-get/post`, `hx-trigger`, `hx-target`, `hx-swap` (closed enum innerHTML/outerHTML/…/none), `hx-confirm`, `hx-indicator`, `hx-disabled-elt`, `hx-push-url`; server-side `HX-Redirect`/`HX-Location`. HATEOAS: "the server tells the client what it can do next." | Which controls exist in a given state — that is the server's response, i.e. the behaviour model decides enablement. | Enablement moved back to the server (the domain): the client only declares *what to do with the answer*. Note `hx-confirm`, `hx-indicator`, `hx-disabled-elt` are sense-C idioms expressed as flat closed attributes. | [htmx docs](https://htmx.org/docs/) |

Pattern: the survivors are either (i) a *closed* state×event table with no presentation in it, (ii) a screen graph drawn *on* the pixels rather than instead of them, or (iii) a *default* the code can override. None of them is an abstract container, none has a task algebra, and the two that grew conditionals (Figma, ECA) are the ones on the slope.

### "Anything with bespoke interaction fell off a cliff" — what exactly fell off

The brief's phrase is a paraphrase; Myers' words are that automatic and model-based systems "have each placed significant limitations on the kinds of interfaces they can produce", after noting that the lineage began with tools that "generated the dialogs to display and request the data" ([Myers 2000 §2.3.4](http://www.cs.cmu.edu/~amulet/papers/futureofhci.pdf)). Read against the dialects, what fell off is concrete: (1) **direct manipulation** — drag, in-place editing, canvases (none of CTT/MARIA/W3C interactor taxonomies has a construct for it; the vocabularies stop at select/edit/trigger/output); (2) **feedback timing** — optimistic vs. confirmed, progressive disclosure, animation (MARIA's only nod is a `continuously-updated` attribute); (3) **compound idioms** — undo, drafts, multi-step with back-tracking, which need a state machine richer than "transition task → next presentation set"; (4) **cross-cutting navigation chrome** — the site-wide navigation bar Cameleon's reverse-engineering had to special-case ([D2.1 p.32](http://giove.isti.cnr.it/projects/cameleon/doc/CAMELEON%20D2.1.pdf)). Everything that survived generation was a form, a list, a menu and a link — the Rails scaffold.

## 4. Relevance to senses A, B, C

### A. Navigation topology
*Ancestors:* Cameleon's Presentation Task Sets and transition tasks; ARTStudio's derived navigation scheme; UsiXML `navigation` facet and dialog-transition relationship; MARIA `navigator` interactor and connections; Figma flows and wireflows as the surviving human form.
*Fate:* Navigation was **derived** from the task algebra everywhere it was tried, then patched by human override. This confirms H-A's shape: the derivable part is large (which surfaces are reachable after which command follows from command→event→view chains and `phase`), and the authored residue is (a) *entry point per flow* — Figma's "starting point", ARTStudio's root workspace — and (b) *post-command destination* — Rails' redirect convention, htmx `HX-Redirect`, Cameleon's `(transition_task, next_PS)` rule. The ancestors predict two dangers: a per-surface transition list re-creates the dialog state machine (F1), and a `wizard`/`master-detail` pattern name is one step from `window`/`canvas` (F3). A defensible residue is a closed enum on a **command** (return / advance / stay), not a graph on surfaces, and an `entry:` per persona; both should be tested against Dead-weight on the three testbeds before admission.

### B. Dialog / state model
*Ancestors:* UIDE pre/post-conditions; CTT enabling/disabling/suspend-resume; UsiXML state machine and ECA rules; MARIA per-presentation dialog model; W3C AbstractListener; Harel statecharts as the survivor.
*Fate:* Every MBUI dialog model was a second copy of the application's behaviour (F2) that then needed a predicate language (F1). Schlungbaum's definition — the dialogue model "describes when the end-user can invoke commands… the sequencing of input tokens, output tokens and their interleaving" — is exactly what emlang's deciders, `phase` enum and GWT scenarios already encode. The survivor (statecharts) survived by *being* the behaviour model, not annotating it. Prediction for H-B: anything xmlang adds is either derivable from emlang or a `when:` in disguise; the only historically stable residue is the *coarse* activation lattice xmlang already has (`during` × `for`), which is the W3C AUI's "compositionRole" done as a closed enum rather than an ECA rule. If a dialog fact is missing, the evidence says it belongs in emlang (a phase, a decider precondition, a GWT scenario), which is a legitimate "this belongs in emlang" finding.

### C. Interaction idioms
*Ancestors:* MARIA `only_output` subtypes (feedback, alarm), `continuously-updated`; CTT task type + frequency of use; htmx `hx-confirm`, `hx-indicator`, `hx-disabled-elt`, `hx-swap`; Figma `Open overlay` vs `Navigate to`.
*Fate:* The MBUI taxonomies were derivable from type (F9) and died as dead weight; the surviving idiom vocabulary is htmx's — a handful of flat, closed, per-control attributes with no conditions. That supports H-C's split: **destructive confirmation** (`hx-confirm`) and **waiting/disabled-while-pending** (`hx-indicator`, `hx-disabled-elt`) are genuine per-command judgments not computable from the Event Model; **undo** is a compensating command and therefore belongs in emlang; **optimistic vs. confirmed** feedback is transport/timing, already a non-goal. The ancestors' warning: `Open overlay`/`modal`/`inline` are placement (Figma, ARTStudio window-vs-canvas), i.e. disguised geometry and fail test 3; `posture: read-only|editable` is derivable from whether a surface composes any command and fails test 1 unless a testbed shows a non-default case.
