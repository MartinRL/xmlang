## 0. Four facts that set the cost of everything

**F1. EmSpec is flat; half the candidates need slice chains.** `EmParser.Collect` (XM `src/emlang/Emlang/EmParser.cs:94-121`) lifts elements out of steps and *throws away the slice*: it keeps trigger roles (dropping the origin after `/`, L116-121), element names and props, slice keys and the phase-value union. It does not know which command a trigger belongs to, which view ends which slice, or which `given` phases make a command succeed. The post-command destination default (D2), `xm-then-restates-default`, `xm-command-phase-mismatch`, `xm-command-trigger-mismatch`, `xm-then-needs-instance`, trigger-origin resolution and `compensates:` all need that. Call the shared prerequisite **P0: `EmSpec.SliceChains`** — an `EmSliceChain(Name, Triggers[(Role, Origin)], Command, Exceptions, Events, TerminalView, SuccessGivenPhases, RejectionShapes)` list on `EmSpec`. The AST for it already exists: `Emlang.Linting.EmAst` (XM `src/emlang/Emlang/Linting/EmAst.cs:48-51`) parses `EmSlice(Name, Elements in order, Tests)` with GWT. P0 is therefore a projection from `EmAst` into `EmSpec`, not a new parser — size **M**, one-time, and the `EmElement` name clash between `Emlang` and `Emlang.Linting` needs an alias. It changes `ApprovalTests.EmSpecShape` (one snapshot, re-approve). Without P0, every candidate marked "needs P0" below is either uncomputable or a heuristic over element names.

**F2. Snapshot cost of model additions is near zero.** `VerifySetup.cs` has no overrides, so Verify's defaults apply: null members, empty collections and `false` booleans are omitted (visible in `Snapshots/ApprovalTests.XmSpecShape.verified.txt`, where `View: { Name: State / Shop }` prints no `Primary`/`Self`). Adding `Then: string?`, `Confirm: bool`, `Heading: string?`, `Confirm`/`Values` on `XmLabelEntry` leaves all 12 existing snapshots byte-identical until an example *uses* the key. The `SpecExampleTests` index shift (8 blocks, indices 0-7) is avoided entirely by extending the existing example blocks (block 4 = the Dashboard/prominence example, block 3 = `during`, block 6 = labels) instead of adding blocks.

**F3. kvissig never constructs xm records and never reads `During`.** A grep for `new XmCommandItem|new XmViewItem|new XmLabelEntry|.During` over KV `src` returns nothing; the interpreter reads `Surface.Compose`, `Labels[..].Elements[..].Self/Fields/Empty` (KV `Presentation/AuctionSurfaces.cs:41-44, 61-62`). Positional-record additions with defaults are source-compatible; the only KV cost of a model change is the `Xmlang` package bump (`MerEllerMindre.Web.csproj:11`, currently 0.5.0) and whatever the interpreter chooses to *consume*. `XmCatalog` (KV `Xm/XmCatalog.cs:33-37`) throws on lint **errors only**, so new warnings/infos never break the deploy.

**F4. "Generated verification" does not exist yet in either repo.** The spec says labels are "the source of accessible names in generated verification (aria snapshot baselines)" and journeys are "material for generated cross-slice walkthrough tests", but no generator emits either: `Emlang.Generators` emits records and decider tests; KV `MerEllerMindre.Web.Tests` are hand-written endpoint tests using `Should().Contain("name=\"amount\"")` (`AuctionEndpointsTests.cs:168`). The "generated-verification change" column below therefore describes what a future harness *would* assert, and its first line item is the harness itself (L, independent of every candidate).

## 2. Transformer-neutrality (test 5) per candidate

| Candidate | Codegen | Runtime interpreter | Human/agent hand-building | Verdict |
|---|---|---|---|---|
| K1 `then` | emits the redirect target per command handler; trivially meaningful | overrides state-driven selection after a command; meaningful, small | "after Submit, go back to the inbox" is exactly a sentence a designer writes in a flow doc | neutral |
| K2 `confirm` | emits a confirm step in the handler or a client attribute | `hx-confirm` / dialog | "ask first" | neutral. **Flag**: the *form* of assent (dialog, inline, typed re-entry) is where the three diverge; the spec must keep it transformer-defined |
| K3 `heading` | emits `<h1>{field}</h1>` / aria-label binding | resolves at render | "the invoice number is the page title" | neutral. Flag: for codegen and runtime it is trivially "which field"; for a human it shades into layout unless the spec says *name*, not *region* |
| L1-L3 labels | resource bundles | dictionary lookup | copy deck | neutral by construction (labels already are) |
| L4 ICU | needs a MessageFormat runtime in the target language | same | a human reads `{count, plural, …}` fine; an agent too | neutral in meaning, **unequal in cost**: only machine transformers pay the formatter dependency, and .NET has none built in |
| R1, R2, R3, R4, R5 | lints run at build time for all three; a human runs `xm lint` | same | same | neutral |
| D1 fine selector | generates the selector function | must implement the cursor — the only transformer that pays at runtime | reads the paragraph, hand-writes the seven lines (as all three C1 probes did) | neutral in meaning; **only the runtime interpreter pays an engine cost**, which is why D1 should be prose and a checkable rule, not a required engine |
| D2 destination default | generates redirects | seeds selection | reads it | neutral |
| E1-E4 | all three consume a richer Event Model | same | same | neutral; the cost sits in emlang tooling (Go + .NET + fmt), not in transformers |

Nothing here makes sense for only one transformer kind. Two things make sense for all three but *cost* only one: L4 (machine formatter) and a D1 engine (runtime). Both are reasons to keep the spec text at the level of rule, not mechanism.
