# Red team: the four emlang RFCs

Adversarial review of `rfcs/emlang-000{1..4}-*.md`. Counts re-derived mechanically (PyYAML, scratchpad `rt.py`/`rt2.py`).

Event Modeling text relied on, quoted. Cheatsheet: Automation is "Event(s) -> View -> Automated Trigger -> Command -> Event(s)", and "the view that the automated process monitors, is a simple todo list. For each row the automated process calls a use case, which provides a new event". "What is Event Modeling": "The wireframes are generally put at the top of the blueprint. They can be divided into separate swimlanes to show what each user sees"; "All information has to have an origin and a destination"; GWT illustration "**Given**: We have registered, and added a payment method". Neither page names state, aggregates or deciders.

---

**R1 — RFC 0001, whole RFC. blocks.** Claim: "Shipping them as a fork, or as an unmarked linter config, loses the property that a v1.0.0 tool can still read the file" (0001:19). emlang already has a marked per-project linter config: `.emlang.yaml` with `lint.ignore` and `fmt.keys` (Go `internal/config/config.go:10-25`, README "Configuration"; ported locally in `Emlang.Cli/Program.cs:63-71`, shipped in `0ecdb11`). `lint.profile: decider` there costs no schema edit, no formatter work, and fails no validator — which is RFC 0001's own open objection 3. No RFC in the set mentions the file; the Rejected-alternative section weighs only a comment header. Objection C's strongest form is not answered, it is unseen. Answer: name one fact a profile must carry *in the document*, or withdraw the root key.

**R2 — RFC 0001 §1 vs §2. blocks.** "an unknown profile name MUST be reported as an error" against "This specification defines no profile". A conforming 1.1.0 tool that has not implemented RFC 0002 MUST error on `profile: decider`. The header converts v1.0.0's tolerable "unknown root key" into a hard conformance failure on *newer* tools, with no ignore mode. Answer: unknown profile = warning, process as base version.

**R3 — RFC 0001 §2 vs RFC 0002 objection 3. blocks.** 0001: "a profile MUST NOT relax, remove or redefine a base rule". 0002: "the profile changes what `given` means: in v1.0.0 a `given` is 'Pre-conditions (events, views)' … in the profile a decision test's `given` is the decider's state". The drafter states the violation. Answer: rewrite the bullet as "MUST NOT widen the set of valid documents; MAY narrow the meaning of a base construct".

**R4 — RFC 0002 §2, the 1:1 map. blocks.** "its `given` MUST be empty or exactly one state element" — nothing requires that state's decider to own the emitted events. `lob-ap.em.yaml:292-340`: `DraftInvoice` gives `v: State / Supplier` (`:324`, `:334`) and emits `e: Invoice / InvoiceDrafted` (`:331`). Fully conforming, and exactly the cross-decider decision §2 rejects when there are three states. The profile bans reading three deciders and permits reading the wrong one. RFC 0004:62 spots the symptom and refers it back to 0002, which never rules. Answer: require the given state and the `then` events to name one decider, or drop the 1:1 claim.

**R5 — RFC 0002 §3, fold by reference. blocks.** "`em-state-without-fold` fires on none of the 185 tests" — true and empty, because the check is name-level. The RFC's charge against events-givens is that such a test "pins neither"; a name-level fold reference pins nothing either. Phase values pinned in decision givens that no fold test in the file produces: lob-ap `draft` (8 givens), `approved` (7), `rejected` (1), `scheduled` (1) — 17 of 40; games `lobby` (4/5/4). Every model passes while most pinned states are undemonstrated. Answer: require each *phase value* in a given to be produced by a fold test, and publish the real baseline (17/4/5/4).

**R6 — RFC 0002 §4, the Todo smell. weakens.** "A `Todo /` view in a decision test's `given` is a smell." EM's Automation pattern is "Event(s) -> View -> Automated Trigger -> Command", and its view is "a simple todo list. For each row the automated process calls a use case." The Todo *is* the automation's decision information in the method the DSL is named for; lob-ap models it so (`:907-912`). The profile declares the canonical pattern illegitimate on three instances in one model, with the correct form asserted (`phase: scheduled`) and never written. Answer: reduce to "a Todo given SHOULD be accompanied by the decider state the command validates against", or withdraw.

**R7 — RFC 0002 §3/§5 vs RFC 0004 Conventions. weakens.** 0002 scopes fold-by-reference and phase uniqueness to "the same file"; 0004 says "'document' means one YAML document, not the file"; SPEC L238 says "Each document MUST independently conform"; 0001 says the header "applies only to the document that carries it". So a profile document's fold may legally sit in a non-profile document of the same file. Answer: pick one scope across all three RFCs.

**R8 — RFC 0002 §5, `em-phase-ambiguous`. weakens.** "Phase values are namespaced by decider", then "a bare phase value declared by … more than one decider … MUST be reported as an error". The namespace is declared and then forbidden. Two deciders that both have `draft` (purchase order and invoice) become an error — not because the model is confused but because xmlang's *list* form of `during` would be, and xmlang RFC 0001 §5 already ships the map form. A consumer's convenience imposed as a spec error. Answer: demote to warning.

**R9 — RFC 0002 §1 form A. weakens.** "a state element … MUST NOT be composed as a screen." `compose` is an xmlang key; emlang has no screens or surfaces. A profile of emlang legislating xmlang composition is the layering violation the RFC set otherwise defends. Answer: delete the clause.

**R10 — RFC 0002 §1 form B. blocks (for B).** Conceded in-RFC: "If B is chosen, `s:` MUST be added to the base spec … the profile itself cannot introduce a kind." Then 0002-B is a base-spec element-kind change wearing a profile, and the plan's stand-alone claim fails. EM's picture has four patterns and no state box, so `s:` is the first kind with no canvas counterpart. Answer: withdraw B; keep the re-open condition from `cut-lines.md` §B.

**R11 — RFC 0002, dual specification. weakens.** "A state element's `props` declare the decider's folded state" — nothing generates or checks them. `SpecModel.cs:19-20`: "'v' elements are inert for record emission"; the state record's name is a convention (`EmitTarget.cs:14`) and its shape is hand-written C#. Two homes for one fact, no check either way: the MBUI failure mode. Form B worsens it — a dedicated kind asserting a shape nothing verifies. `StateType` is also single-valued per spec, so "multi-decider models are legal" legalizes documents the reference generator cannot emit. Answer: say state props are documentation until a generator emits the record; rule multi-decider codegen out of scope.

**R12 — RFC 0002 §3 vs upstream's own rule list. blocks.** The profile makes the Decision Model slice mandatory; EM's canvas has no such artefact (all four patterns are timeline slices) and the models mark it "APPENDIX, not timeline steps" (`lob-ap.em.yaml:1259`). Upstream's README rule table lists `test-missing-command` | **error** | "Test without command (when)" — every fold test is a test without `when` — and `slice-missing-event` (implemented, warning) fires on every such slice, 13/9/11/9, which RFC 0004:176 records and declines to change. The profile requires an artefact upstream's documented lints condemn. Answer: propose retracting `test-missing-command` and exempting decision slices, or the profile is unadoptable upstream.

**R13 — RFC 0002 §2 vs the method's GWT. weakens.** EM's worked specification is "**Given**: We have registered, and added a payment method" — prior facts, not folded state; the spec's own `EmailMustBeUnique` gives an event. A decider-only given is defensible engineering but a departure from the method, presented in Motivation as a restatement of practice. Answer: state the departure and the reason.

**R14 — RFC 0002 Implementation notes, `em-state-name-slash`. weakens.** "a state named `State / Order/Line` is `Order/Line` to `em lint` and `Line` to `xm`." Wrong where it matters: `EmParser.Split` takes the last slash (`EmParser.cs:37`), so the lane becomes `"State / Order"` and `PhaseValues` filters `Lane == "State"` (`:147`) — the element stops being a state for `xm` and the generator. Not a name disagreement, a disappearance. The divergence also hits every event, view and origin, so a state-only rule is a spot patch for a local bug exported into a spec. Answer: fix the three last-slash sites; drop the rule.

**R15 — RFC 0003 §B. weakens.** The origin is where the actor was standing: an experience fact. The RFC concedes the consumer case — "every derivation RFC 0001 admits is computable from `compose` alone … the emlang origin only adds the modeller's statement of where the actor was, which a transformer can verify against `compose` or ignore." The counter is that EM's wireframe row is part of the blueprint, and it is — but a free-text string after a slash is not that row, and making it a resolvable reference imports a fragment while the rest stays in xmlang: dual specification with the seam in the worst place. Answer: keep the origin unlinted in emlang; put resolution in xmlang.

**R16 — RFC 0003 §B, the bare form. weakens.** "the origin equals the slice's command name … `Player /JoinAuction` is a declaration", admitted to "read oddly and [be] a convention, not a construct". It exists so `em-trigger-origin-unresolved` can reach a clean baseline and rise to error; rule and escape hatch are designed around each other, and the hatch renames three real screens ("Join form") to command names. A lint dictating a model's vocabulary. Answer: take Alternative A and accept a permanently non-zero baseline, or withdraw §B.

**R17 — RFC 0003 §A, the fixture fix. weakens.** "add `t: 🧑‍🏫 host /Round scores`" because "all three shipped UIs give the host a button". The evidence that the Event Model is wrong is three game UIs, and games are the maintainer's declared negative control. The alternative reading — the button is an affordance over a System-paced loop and the model is right — is never considered; the edit lands only because an xmlang enablement default would hide the button, i.e. the model is edited to satisfy the transformer. Answer: show one LOB dual initiator, or record the fix as an xmlang convenience.

**R18 — RFC 0004, `em-actor-identity`. weakens.** "`<role>Id`, where `<role>` is a trigger role … in lowerCamel" and "the unique prop that starts with a trigger role's name, case-insensitive". Every model's role carries an emoji — `🧑‍🎓 Player`, `🧑‍🏫 host`, `🧾 Clerk` (`blindbudet.em.yaml:343`, `lob-ap.em.yaml:294`) — and lane text is compared verbatim downstream (`XmLinter.cs:38`). `"playerId".StartsWith("🧑‍🎓 Player")` is false. Unimplementable as written, and proposed at **error** under the profile. Answer: define role normalization in the rule text.

**R19 — RFC 0004, `em-view-information-incomplete`. weakens.** Named after EM's completeness rule, which is two-sided — "All information has to have an origin and a destination" — while the check tests origin only and leaves destination manual. Half a principle at 40/11/13/10 findings, mostly `gameId`. Answer: rename `em-view-prop-untraced` and stop claiming EM's completeness check.

**R20 — RFC 0004, `(@param)`. weakens.** `phaseFilter`, `supplierFilter`, `dueBefore`, `query`, `statusFilter` (`lob-ap:64-65`, `:1126-1129`) are what the user asked to see — screen state — and the consumer clause is purely negative ("xmlang never tiers a `(@param)` prop"). xmlang can decline to tier props without emlang's help. `asOf`/`viewerId` are a different kind (projection clock and identity) and are lumped in. Answer: split the two kinds; keep projection arguments, drop UI filters.

**R21 — RFC 0004, status vs severity. blocks.** Titled "Lint rules, a non-normative appendix", it assigns `em-param-note-malformed` error in both columns and `em-actor-identity` error *under a profile defined in RFC 0002* (which deferred it here, 0002 §6). A non-normative appendix cannot make a document non-conforming, and a later RFC re-severitying an earlier profile breaks independence outright. Answer: move error-severity profile rules into 0002.

**R22 — Independence. blocks.** Real couplings: 0004 indexes and re-severities rules from 0002 and 0003 (0004:177-190); 0003's frontmatter credits its `profile: decider` column to RFC 0001, which "defines no profile" — the dependency is 0002; 0002-B needs 0001's strip rule and the base spec amended; 0002 §5's consumer story needs xmlang RFC 0001 §5's map form. Only 0003 §A stands alone. Answer: publish the real graph (0001 → 0002 → {0003 §B severity, 0004}) and drop "accept or reject alone".

**R23 — Evidence quality. cosmetic, with credit.** Independently re-derived: given shapes 54 events / 105 single-state / 1 multi-state / 3 Todo / 22 empty / 0 mixed / 185 tests — matches RFC 0002 exactly, including the three-state given. No `when` test gives events; no `when`-less test gives state. Triggers 43 total, 19 resolved (18/20, 0/7, 0/9, 1/7), 24 unresolved split 12 System / 9 human / 3 join — matches RFC 0003. No slice has two triggers (85 slices). `- v: State /` counts 48/23/27/25 = 123 — matches. RFC 0004's lob-ap Invoice matrix reproduces cell for cell (13 success / 10 rejection-only / 94 none), as do blindbudet (6/1/14) and the Supplier projection (4/3/3). Around thirty spot-checked citations are correct (`lob-ap:1267`, `:685-692`, `:1283`, `:1263`, `:577`, `:1034`, `:1150`, `:1100`; `blindbudet:7`, `:23-24`, `:121`, `:305`, `:343`, `:526`, `:920-926`, `:946`; `mer:24-27`, `:273`, `:1291-1293`; `tank:21-24`, `:310`, `:1009-1015`). Three misses: RFC 0003's census says the Todo is "read at 909" and "read at 1095", but those lines are the *events* — the Todo views are at 910 and 1096; and RFC 0002's lint table cites `em-given-todo` at `:931, :943, :1108` (test-name lines) against its own §4's `:933, :945, :1110` (elements), with RFC 0004:181 copying the former. Answer: fix four lines.

**R24 — Evidence base. weakens.** Each RFC's objection 1 admits it: 185 tests, four models, one team, three of them the declared negative control. RFC 0002's Migration then notes the first `em fmt -w` normalizes `State / Game` to `State/Game`, so "every line number cited in this RFC and in the census moves". The evidence invalidates its own citations on the first format, before a second modeller has written a line. Answer: format the fixtures and re-cite; get one model from someone else.

---

## Verdicts

- **RFC 0001 (profiles): redraft.** R1 (`.emlang.yaml` never considered) and R2 (unknown-profile error inverts the compatibility promise) hit the mechanism; R3 is a rule the next RFC violates.
- **RFC 0002 (decider profile): accept with named fixes**, form A only, not before R4 (cross-decider given) and R12 (`test-missing-command`) are answered; plus R5, R6, R7, R8, R9, R14. Form B: withdraw (R10).
- **RFC 0003 (trigger origin): §A accept as drafted** minus the fixture fix (R17). **§B redraft as an xmlang cross-check, or withdraw** (R15, R16).
- **RFC 0004 (lints): accept with named fixes** — R21 (a non-normative appendix cannot carry error severities), R18, R19, R20, R23.

## How much of RFC 0003 should move to xmlang

Most of Section B, none of Section A. Who may issue a command is a domain authorization fact and the shape is already legal: §A stays. The origin is where the actor stood, a surface fact, and the RFC concedes every xmlang default is computable from `compose` alone. So emlang keeps the origin as free text plus one base-spec naming rule (swimlane = text before the first `/`; no second `/` in a name) because that is a real gap independent of experience; xmlang gains the resolution rule as its own lint — `xm-origin-mismatch`, warning: a command's emlang origin names a view no surface composing that command composes. The bare-form declaration goes entirely: a convention invented to clean one lint's baseline is not a spec fact.

## The single strongest objection

The decider profile's only enforcement surface is a linter, and emlang already ships a per-project linter configuration file — `.emlang.yaml`, with `lint.ignore` and `fmt.keys`, in the Go reference (`internal/config/config.go:10-25`, README "Configuration") and in the maintainer's own `em` (`Emlang.Cli/Program.cs:63-71`, `0ecdb11`). `lint.profile: decider` there delivers every rule in RFCs 0002 to 0004 at zero schema cost with no document failing any existing tool — precisely the failure RFC 0001 records as its own open objection 3. The RFC set never mentions the file. Until RFC 0001 names one fact a profile must carry in the document and cannot carry in the config — and "the meaning of `given` changed" is a claim about rules, not documents — the root key is a schema bump bought to hold a setting that already has a home.
